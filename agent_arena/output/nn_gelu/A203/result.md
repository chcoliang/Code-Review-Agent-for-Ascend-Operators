# GELU DAG 算子代码审查报告

**文件**: `gelu_dag.h`  
**平台**: Ascend 910B  

---

## Bug 1: TANH_APPROX_FACTOR 声明为 int 导致精度截断

- **位置**: 第 25 行
- **类型**: 精度错误 / 类型错误
- **严重程度**: 高
- **描述**: `const int TANH_APPROX_FACTOR = 1 / 0.044715;` 将浮点除法的结果（约 22.3629）截断为整数 22。该常量在第 55 行的 `Axpy` 运算中被用作缩放因子，导致计算公式变为 `x³ + 22*x` 而非正确的 `x³ + 22.3629*x`。最终经过后续乘法后，GELU 公式中的线性系数从正确的 ~1.5958 变为 ~1.5699，引入约 1.6% 的系统性精度误差。
- **触发条件**: 所有输入均会触发，对任意非零输入 x 都存在精度偏差，且 |x| 较小时相对误差更显著（因为线性项主导）。
- **修复建议**: 将类型改为 `const float TANH_APPROX_FACTOR = 1.0f / 0.044715f;`
- **测试方案**: 
  1. 对比标准 GELU 实现（PyTorch/numpy），在 x ∈ [-3, 3] 范围内均匀采样，检验最大绝对误差和相对误差。
  2. 预期修复前最大相对误差 > 1%，修复后应 < 0.1%（float精度范围内）。

## Bug 2: 循环中 count 未递减导致 Mask 计算错误

- **位置**: 第 50 行
- **类型**: 计算逻辑错误
- **严重程度**: 高
- **描述**: 在 for 循环（第 49 行）中，每次迭代调用 `UpdateMask<T, MicroAPI::RegTraitNumOne>(count)` 时使用的是原始的 `count` 值，从未按 `count -= vl` 递减。当 `count > vl`（即数据量超过一个向量寄存器宽度）时：
  - 若 `UpdateMask` 对超过 vl 的 count 取 min(count, vl)，则最后一次迭代本应使用 `count % vl` 的 mask，却仍使用满 mask，可能读写越界数据。
  - 若 `UpdateMask` 直接使用 count 值而不做截断，则每次迭代都使用错误的 mask 宽度，导致计算结果完全错误。
- **触发条件**: 当处理的元素数量 `count > vl`（即 count > 64 for float, vl = 256B/4B = 64）时触发。单 block 内数据量大于 64 个 float 元素时必现。
- **修复建议**: 在循环末尾添加 `count -= vl;` 或在 mask 计算时使用 `UpdateMask<T, MicroAPI::RegTraitNumOne>(min(count - loopIdx * vl, vl))`。
- **测试方案**:
  1. 构造 count = 128（大于 vl）的测试用例，对比输出后半段（第 65~128 个元素）是否正确。
  2. 构造 count = vl + 1 的边界用例，检查最后一个元素是否正确处理、是否有越界写入。

## Bug 3: 常量命名与实际语义不符（低风险）

- **位置**: 第 24 行
- **类型**: 代码可维护性 / 命名误导
- **严重程度**: 低
- **描述**: 常量名 `NEG_SQRT_EIGHT_OVER_PI` 含义为 `-sqrt(8/π)`（≈ -1.5958），但实际赋值为 `-1.595769121 * 0.044715`（≈ -0.07136）。这是将 `-sqrt(8/π)` 与 `0.044715` 预乘后的复合常量，命名未反映乘以 0.044715 的事实，容易误导后续维护者。
- **触发条件**: 不影响运行时行为，影响代码可读性和可维护性。
- **修复建议**: 重命名为 `NEG_SQRT_EIGHT_OVER_PI_MUL_COEFF` 或添加注释说明。
- **测试方案**: 代码审查即可，无需运行时测试。
