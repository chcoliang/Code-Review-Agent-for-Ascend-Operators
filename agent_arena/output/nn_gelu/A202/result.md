# Code Review: gelu_dag.h

## Bug 1: 常量精度错误 — NEG_SQRT_EIGHT_OVER_PI 中 0.04471 应为 0.044715
- **位置**: 第24行
- **类型**: 精度问题/常量错误
- **严重程度**: 中
- **描述**: `NEG_SQRT_EIGHT_OVER_PI = -1.595769121 * 0.04471`，其中 `0.04471` 与第25行和第29行注释中使用的 `0.044715` 不一致。GELU 的近似公式为 `x / (1 + e^(-1.5957691 * (x + 0.044715 * x^3)))`，代码将其分解为 `x / (1 + e^(-1.5957691*0.044715 * (x/0.044715 + x^3)))`。因此 NEG_SQRT_EIGHT_OVER_PI 应等于 `-1.595769121 * 0.044715`，但实际使用了 `0.04471`（少了一个 `5`），导致系数偏小约 0.01%，在大输入值时会产生可观察到的精度偏差。
- **触发条件**: 输入较大绝对值的 x（如 x=3.0 或 x=5.0），对比标准 GELU 实现的输出，会发现数值差异。
- **测试方案**: 构造 x ∈ {-5.0, -3.0, -1.0, 1.0, 3.0, 5.0} 的输入 tensor，计算该算子输出与 PyTorch `torch.nn.functional.gelu(x)` 的绝对误差，验证误差是否超出正常 float 精度范围（期望发现 ~0.01% 相对误差）。

## Bug 2: 循环内 Mask 未根据迭代进度更新，导致越界访问或计算错误
- **位置**: 第50行
- **类型**: 计算逻辑错误/内存访问越界
- **严重程度**: 高
- **描述**: `mask = MicroAPI::UpdateMask<T, MicroAPI::RegTraitNumOne>(count)` 在每次循环迭代中都传入总的 `count`，而没有根据当前迭代计算剩余元素数。正确做法应为：对于非最后一轮迭代，mask 应覆盖完整的 `vl` 个元素；对于最后一轮迭代，mask 应仅覆盖 `count - loopIdx * vl` 个剩余元素。当前实现有两个问题：(1) 当 `count > vl` 时，非最后一轮的 mask 行为取决于 UpdateMask 对超过 vl 的 count 的处理方式，可能仅处理 `count % vl` 个元素（即少处理数据）；(2) 最后一轮迭代可能处理了多余的元素，导致读取无效内存数据或写入越界。
- **触发条件**: 输入 tensor 的元素个数 count 大于一个向量寄存器宽度 vl（如 float 类型下 vl=64，输入 count=128 或 count=100 等非对齐值）。
- **测试方案**: 构造元素个数为 `vl + 1`（如65个float元素）的输入 tensor，验证所有元素是否都被正确计算。再构造 `2*vl`（128个元素），验证前 vl 个元素的结果是否正确（若 mask 错误会导致前半部分也计算不完整）。

## Bug 3: 输出 Cast 使用 CAST_MODE_RINT 会将浮点结果四舍五入为整数
- **位置**: 第77行
- **类型**: 类型转换错误
- **严重程度**: 高
- **描述**: `OpResultCast` 定义为 `Vec::Cast<U, T, CAST_MODE_RINT>`，其中 `CAST_MODE_RINT`（第27行定义为1）表示取整模式。当模板参数 U 为 half（float16）时，从 float 转换回 half 应使用 `CAST_MODE_NONE`（普通精度转换），而非 RINT（四舍五入到最近整数）。使用 RINT 模式会将 GELU 的浮点输出（如 0.841）截断为整数（1.0），完全破坏计算结果的精度。GELU 输出范围通常在 [-0.17, +∞)，大部分值为非整数，使用 RINT 会导致几乎所有输出值错误。
- **触发条件**: 使用 half (float16) 作为输入输出类型 U 实例化 GeluDAG（这是最常见的使用场景），输入任何非零值（如 x=0.5，GELU(0.5)≈0.345 会被舍入为 0.0）。
- **测试方案**: 以 float16 类型输入 x = [0.1, 0.5, 1.0, 1.5, 2.0]，验证输出是否为正确的 GELU 值（期望发现输出全被取整为整数值如 0, 0, 1, 2, 2，与正确值 0.054, 0.345, 0.841, 1.397, 1.955 严重不符）。
