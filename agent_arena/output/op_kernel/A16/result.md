# Mul DAG 代码审查报告

## Bug 列表

### Bug 1: MulUint8Op DAG 类型不匹配 — AndFF 使用 int32_t 但上游产出 uint32_t

- **位置**: 第 460 行 `using Y1 = Bind<AndFF<int32_t>, Y>;`
- **类型**: DAG 类型匹配错误
- **严重程度**: 高
- **描述**: `Y` 的类型为 `Vec::Mul<uint32_t>` 产出 `uint32_t`，但 `AndFF<int32_t>` 声明输入输出类型为 `int32_t`。DAG 框架进行类型检查时会产生编译错误或隐式截断/未定义行为。应使用 `AndFF<uint32_t>`（代码第 462 行注释中已给出正确写法但被注释掉）。
- **触发条件**: 任何 uint8 类型的 Mul 算子调用。
- **测试方案**: 使用两个 uint8 tensor 执行 Mul，检查编译是否通过及结果正确性（如 200*2 应得到 144 即 400 & 0xFF）。

---

### Bug 2: MulUint8Op DAG 类型不匹配 — Cast 源类型与实际类型不一致

- **位置**: 第 463 行 `using Y2 = Bind<Vec::Cast<uint8_t, uint32_t, CAST_MODE_NONE>, Y1>;`
- **类型**: DAG 类型匹配错误
- **严重程度**: 高
- **描述**: `Y1` 是 `AndFF<int32_t>` 的输出，类型为 `int32_t`。但 `Vec::Cast<uint8_t, uint32_t, ...>` 期望源类型为 `uint32_t`。类型不匹配导致编译失败或数据解释错误。应将 AndFF 改为 `AndFF<uint32_t>` 以统一类型链。
- **触发条件**: 同 Bug 1，任何 uint8 Mul 调用。
- **测试方案**: 同 Bug 1。

---

### Bug 3: MulDouble 规格化数 lshift==0 分支中舍入值被重复累加

- **位置**: 第 340-347 行（`else` 分支，即 `lshift == 0` / `n == 20`）
- **类型**: 逻辑错误（计算精度）
- **严重程度**: 高
- **描述**: 第 342 行先将舍入值加到 `mc_low`：`mc_low += ((s1 >> 1) + (1 << 30)) >> 31;`。随后第 344-346 行又计算相同的 `s2value` 并再次累加到 `mc_low`。这导致舍入值被加了两次，结果偏大 1 ULP。对比 `lshift > 0` 和 `lshift < 0` 分支的模式可知，正确做法是删除第 342 行的累加，仅保留带进位检测的加法（344-347 行）。
- **触发条件**: 两个 double 相乘，乘积尾数的 MSB 恰好在 bit 20 位置（即 `n == EXP_OFFSET == 20`），例如 `1.0 * 1.5` 等特定数值组合。
- **测试方案**: 构造 `n == 20` 的用例（如 mantissa 乘积高位恰为 `0x001xxxxx`），对比硬件 double 乘法结果，验证 ULP 误差。

### Bug 4: MulDouble NaN 输出时 c.i[0] 未初始化

- **位置**: 第 121-129 行（NaN 处理分支）
- **类型**: 未初始化变量
- **严重程度**: 中
- **描述**: 当检测到输入为 NaN 时，仅设置 `c.i[1] = NANI` 而未设置 `c.i[0]`。`c` 为栈上局部变量，`c.i[0]` 包含未初始化的垃圾值，导致输出 NaN 的低 32 位不确定。虽然结果仍为 NaN（因为高位指数全1且尾数非零），但 payload 不可预测，可能导致 bit-exact 测试失败。
- **触发条件**: 任一输入为 NaN 的 double 乘法。
- **测试方案**: 输入 NaN * 1.0，验证输出的低 32 位是否为确定值（应设 `c.i[0] = 0`）。

---

### Bug 5: MulDouble 零值结果丢失符号位

- **位置**: 第 158-167 行（零值处理分支）
- **类型**: IEEE 754 合规性错误
- **严重程度**: 中
- **描述**: 当检测到输入为零时，直接赋值 `c.d = 0`（即 +0.0）。根据 IEEE 754 标准，`(-0.0) * 正数 = -0.0`，`(-0.0) * (-0.0) = +0.0`。当前实现忽略了符号位 `sa ^ sb` 的传播。
- **触发条件**: 输入包含 -0.0 的乘法，如 `-0.0 * 5.0` 应返回 `-0.0` 但实际返回 `+0.0`。
- **测试方案**: 测试 `-0.0 * 1.0`，用 `memcmp` 或检查符号位验证结果为 `-0.0`。

---

### Bug 6: MulDouble __builtin_clz(0) 未定义行为

- **位置**: 第 266 行 `int n = NOSIGN_OFFSET_32 - __builtin_clz(s3);`
- **类型**: 未定义行为 (UB)
- **严重程度**: 中
- **描述**: 当乘积为零时（`total_shift` 路径中的 else 分支，第 222-224 行将 `s3 = 0`），代码继续执行到第 266 行调用 `__builtin_clz(0)`。C/C++ 标准明确规定 `__builtin_clz(0)` 是未定义行为。虽然前面零值检查（第 158-167 行）应该已经 continue 跳过，但如果两个 subnormal 数相乘可能乘积极小导致 s3=0 而未被零值检查拦截（因为输入不为零但乘积下溢为零）。
- **触发条件**: 两个极小的 subnormal double 相乘，乘积完全下溢为零（所有 s0-s3 均为 0）。
- **测试方案**: 测试 `5e-324 * 5e-324`（最小 subnormal 相乘），检查是否崩溃或返回错误结果。

---

### Bug 7: MulBoolOp 使用无效的 CAST_MODE_ROUND 舍入模式

- **位置**: 第 479 行 `using YCast = Bind<Vec::Cast<int8_t, half, CAST_MODE_ROUND>, Y>;`
- **类型**: 参数错误
- **严重程度**: 低
- **描述**: `CAST_MODE_ROUND` 值为 4，在 AscendC 的 `RoundMode` 枚举中，标准舍入模式为 `CAST_NONE(0)`、`CAST_RINT(1)`、`CAST_FLOOR(2)`、`CAST_CEIL(3)`。值为 4 可能不是合法的 RoundMode，或对应的模式语义不适合 bool 乘法。对于 bool 类型（0/1），乘法结果只有 0 或 1，使用 `CAST_RINT`（四舍五入到最近偶数）即可满足需求。
- **触发条件**: bool 类型的 Mul 运算。如果 CAST_MODE_ROUND=4 在目标平台不被支持则会出错。
- **测试方案**: 执行 bool tensor 乘法，验证 `true * true = true`，`true * false = false` 的正确性。
