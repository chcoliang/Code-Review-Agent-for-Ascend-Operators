# mul_dag.h 代码审查报告

## Bug 列表

### Bug 1: NaN 返回值 c.i[0] 未初始化

- **位置**: 第 121-129 行, 第 134-137 行, 第 147-149 行
- **类型**: 未初始化变量
- **严重程度**: 高
- **描述**: 当检测到输入为 NaN 或 inf*0 时，代码仅设置 `c.i[1] = NANI`，但 `c.i[0]`（double 低 32 位）从未被初始化。`U c;` 是局部变量，其成员默认未初始化，导致输出 NaN 的低 32 位为随机垃圾值。虽然结果仍然是 NaN，但不符合 IEEE 754 标准的 canonical NaN（应为确定值），且不同运行结果不一致。
- **触发条件**: 任一输入为 NaN，或 inf 与 0 相乘。
- **测试方案**: 输入 `(NaN, 1.0)` 或 `(inf, 0.0)`，多次运行检查输出的位模式是否一致，验证 `c.i[0]` 是否为 0。

### Bug 2: 零值乘法结果丢失符号位

- **位置**: 第 158-167 行
- **类型**: 逻辑错误
- **严重程度**: 中
- **描述**: 当输入 a 或 b 为零时，代码直接设置 `c.d = 0`（正零），但根据 IEEE 754 标准，零值乘法的结果符号应为 `sign(a) XOR sign(b)`。例如 `(-0.0) * 5.0` 应返回 `-0.0`，`(-3.0) * 0.0` 应返回 `-0.0`，但当前代码始终返回 `+0.0`。
- **触发条件**: 任一输入为 +0.0 或 -0.0，且另一操作数符号为负。
- **测试方案**: 计算 `(-0.0) * 1.0`，检查结果的符号位是否为 1（负零）；计算 `(-5.0) * 0.0`，验证结果为 `-0.0`。

### Bug 3: 规格化数 lshift==0 分支中舍入值被累加两次

- **位置**: 第 339-347 行
- **类型**: 逻辑错误（重复计算）
- **严重程度**: 高
- **描述**: 在规格化数处理的 `lshift == 0` 分支中：
  ```cpp
  mc_low = s2;
  mc_low += ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32; // 第一次加舍入
  unsigned int s2value = ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32; // 同一个值
  int p = (~mc_low < s2value);
  mc_low += s2value; // 第二次加相同舍入值！
  mc_high += p;
  ```
  舍入值被加了两次到 `mc_low`。第 342 行先加了一次，第 346 行又加了一次。对比 `lshift > 0` 和 `lshift < 0` 分支的处理模式（先赋值 mc_low，再计算进位并加一次），此处明显是 bug。正确做法应该是先赋值 `mc_low = s2`，然后只做一次进位检测和累加。
- **触发条件**: 两个 double 相乘，结果的 mantissa 乘积在 s3 中的最高有效位恰好在第 20 位（即 `n == EXP_OFFSET == 20`，`lshift == 0`）。
- **测试方案**: 构造两个 double 值使乘积的 mantissa 命中此分支（如 `1.0 * 1.5`，其中隐含位使 n=20），与标准库 `double` 乘法结果对比最后几位精度。

### Bug 4: MulUint8Op 中 AndFF 类型不匹配

- **位置**: 第 461 行
- **类型**: 类型不匹配
- **严重程度**: 中
- **描述**: `MulUint8Op` 中 `Y` 的类型为 `Vec::Mul<uint32_t>`（输出 `uint32_t`），但 `Y1` 使用了 `AndFF<int32_t>`，其输入输出类型均为 `int32_t`。`uint32_t` 到 `int32_t` 的隐式转换在数值大于 `INT32_MAX` 时会导致未定义行为或符号解释错误。同样，第 464 行的 `Vec::Cast<uint8_t, uint32_t, ...>` 接收的是 `int32_t` 类型（来自 `AndFF<int32_t>` 的输出），存在类型链断裂。注释中已标注了正确应使用 `AndFF<uint32_t>`。
- **触发条件**: 任意 `uint8` 输入执行乘法时均会触发此类型传递问题；当乘积值超过 127 时可能产生错误的截断或符号扩展。
- **测试方案**: 计算 `uint8(200) * uint8(2) = 400`，取低 8 位应为 144 (0x90)，验证结果是否正确。

### Bug 5: __builtin_clz(0) 未定义行为

- **位置**: 第 266 行
- **类型**: 未定义行为
- **严重程度**: 低
- **描述**: 当乘积为零时（`else` 分支，第 222-224 行），`s3` 被设为 0，`total_shift` 为 0，代码继续执行到第 266 行 `__builtin_clz(s3)`。`__builtin_clz(0)` 是未定义行为。虽然理论上非零输入经过零值检查（第 158-167 行）后乘积不应为零，但防御性编程角度仍是隐患。
- **触发条件**: 极端边界情况或编译器优化导致意外进入该分支。
- **测试方案**: 静态分析工具扫描；或在第 266 行前添加 `s3 == 0` 的断言检查。
