# Mul DAG 代码审查报告

## Bug 列表

### Bug 1: 规格化数 lshift==0 分支中 mc_low 被重复累加舍入值

- **位置**: 第 339-348 行，`MulDouble_vf` 函数，规格化数处理的 `else` (lshift==0) 分支
- **类型**: 计算逻辑错误（重复累加）
- **严重程度**: 高
- **描述**: 当 `lshift == 0` 时，代码先在第 342 行将舍入值 `((s1 >> 1) + (1 << 30)) >> 31` 加到 `mc_low` 上，然后在第 344-346 行又计算了相同的 `s2value` 并再次加到 `mc_low` 上。舍入值被加了两次，导致尾数结果偏大。对比 `lshift > 0` 和 `lshift < 0` 的分支，它们只累加一次并正确处理进位，证实此处为笔误。
  ```cpp
  mc_low = s2;
  mc_low += ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32; // 第一次加
  unsigned int s2value = ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32;
  int p = (~mc_low < s2value);
  mc_low += s2value;  // 第二次加，重复！
  mc_high += p;
  ```
  正确做法应删除第 342 行的累加，仅保留带进位检测的 344-347 行逻辑。
- **触发条件**: 两个 double 数相乘，乘积尾数的最高位恰好在 bit 20 位置（即 `n == EXP_OFFSET`，`lshift == 0`），且 `s1` 的最高位为 1（使舍入值为 1）。例如：两个接近 1.0 的正规化数相乘。
- **测试方案**: 构造 `a = 1.0 + epsilon`, `b = 1.0 + epsilon`，使得内部乘积落在 lshift==0 分支，对比硬件双精度乘法结果与该软件实现的输出，验证尾数最低位是否偏差 1 ULP。

### Bug 2: MulUint8Op DAG 中类型不匹配 (uint32_t → int32_t)

- **位置**: 第 460-461 行，`MulUint8Op` 结构体
- **类型**: DAG 依赖链类型不匹配
- **严重程度**: 高
- **描述**: `Y` 节点的输出类型为 `uint32_t`（由 `Vec::Mul<uint32_t>` 产生），但下游 `Y1` 使用 `AndFF<int32_t>`，其输入/输出模板参数为 `int32_t`。在 DAG 框架中，这会导致类型不一致的隐式 reinterpret 或编译错误。注释中已提示应使用 `AndFF<uint32_t>`（第 463 行被注释掉的正确版本）。同样，第 464 行 `Vec::Cast<uint8_t, uint32_t, CAST_MODE_NONE>` 的源类型声明为 `uint32_t`，但实际接收的是 `int32_t` 类型的 `Y1`。
- **触发条件**: 任何 uint8 类型的 Mul 算子调用。当两个 uint8 值的乘积高位为 1（如 200*2=400，低 8 位为 0x90）时，int32_t 的符号解释可能影响后续 Cast 行为。
- **测试方案**: 输入 `x1 = [200, 255], x2 = [2, 2]`，期望输出 `[144, 254]`（取低 8 位），验证是否因类型错误产生错误结果或编译失败。

### Bug 3: NaN 输出时 c.i[0] 未初始化

- **位置**: 第 121-129 行、第 133-137 行、第 144-149 行
- **类型**: 未初始化变量
- **严重程度**: 中
- **描述**: 当检测到输入为 NaN 或 inf*0 时，仅设置 `c.i[1] = NANI`，但 `c.i[0]`（double 的低 32 位）从未赋值。`U c` 是栈上局部变量，`c.i[0]` 包含不确定值。虽然 IEEE 754 中任何 NaN payload 仍是 NaN，但结果不可复现、不可预测，在需要 canonical NaN 的场景中会导致问题。
- **触发条件**: 任一输入为 NaN，或 inf * 0 的情形。
- **测试方案**: 多次调用 `MulDouble(NaN, 1.0)`，检查输出的低 32 位是否一致（canonical NaN 应为全零）。对比标准库行为。

### Bug 4: 零值乘法丢失符号位

- **位置**: 第 157-167 行
- **类型**: IEEE 754 合规性缺陷
- **严重程度**: 中
- **描述**: 当某一输入为零时，代码直接设置 `c.d = 0`，结果始终为 +0.0。根据 IEEE 754 规则，`(-0.0) * 正数 = -0.0`，`(-1.0) * 0.0 = -0.0`。符号应为 `sa ^ sb`。
- **触发条件**: 任一输入为 ±0 且另一操作数符号为负。例如 `-0.0 * 5.0` 应返回 `-0.0`，但实际返回 `+0.0`。
- **测试方案**: 验证 `mul(-0.0, 1.0)` 的符号位；验证 `mul(0.0, -1.0)` 的符号位。使用 `signbit()` 检查。

---

### Bug 5: MulOp 中 X1 经过冗余 Identity Cast 导致 DAG 不对称

- **位置**: 第 375 行，`MulOp` 结构体
- **类型**: DAG 逻辑冗余 / 潜在性能问题
- **严重程度**: 低
- **描述**: `X1Identity = Bind<Vec::Cast<T, T, CAST_MODE_NONE>, InputX1>` 对 X1 做了一次 T→T 的无操作 Cast，而 X2 直接输入 Mul 节点。这导致 X1 路径多一个 DAG 节点，增加了不必要的调度开销和 buffer 占用。虽然功能正确，但在大规模 tensor 计算中会产生可量化的性能损失。
- **触发条件**: 所有使用 `MulOp` 模板的类型（float, int32, int64, int16, complex64）。
- **测试方案**: 删除 X1Identity 节点直接使用 InputX1 作为 Mul 的第一个输入，对比算子吞吐量和正确性。
