# Mul DAG 代码审查报告

## Bug 列表

### Bug 1: NaN 输出时 c.i[0] 未初始化

- **位置**: 第 121-129 行, 第 133-137 行, 第 145-149 行
- **类型**: 未初始化变量
- **严重程度**: 中
- **描述**: 当检测到 NaN 或 inf*0 时，仅设置了 `c.i[1] = NANI`，但 `c.i[0]`（double 低 32 位）未被初始化。`U c;` 声明时未赋初值，导致输出 NaN 的低 32 位为栈上随机值，可能造成非确定性结果。
- **触发条件**: 任一输入为 NaN，或 inf 乘以 0 时触发。
- **测试方案**: 构造输入 `src1 = NaN, src2 = 1.0`，验证输出是否为标准 quiet NaN（`0x7FF8000000000000`）。多次运行检查结果一致性。

### Bug 2: 零值乘法结果丢失符号位

- **位置**: 第 158-167 行
- **类型**: 逻辑错误（违反 IEEE 754）
- **严重程度**: 中
- **描述**: 当 `a` 或 `b` 为零时，直接将结果设为 `c.d = 0`（即 +0.0）。根据 IEEE 754 标准，零值乘法的结果符号应为两操作数符号的异或（例如 `-0.0 * 5.0 = -0.0`，`-0.0 * -3.0 = +0.0`）。当前实现完全忽略了符号处理。
- **触发条件**: 任一操作数为 +0 或 -0 时触发，例如 `-0.0 * 1.0` 应得 `-0.0` 但得到 `+0.0`。
- **测试方案**: 测试 `-0.0 * positive`、`-0.0 * negative`、`+0.0 * negative` 等组合，用 `memcmp` 或位检查验证输出的符号位。

---

### Bug 3: 规格化数 lshift==0 分支中舍入值被重复累加

- **位置**: 第 339-348 行
- **类型**: 逻辑错误（重复计算）
- **严重程度**: 高
- **描述**: 在规格化数处理的 `lshift == 0` 分支中：
  - 第 341 行 `mc_low = s2;`
  - 第 342 行 `mc_low += ((s1 >> 1) + (1 << 30)) >> 31;` —— 第一次加舍入贡献
  - 第 344 行 `s2value = ((s1 >> 1) + (1 << 30)) >> 31;` —— 计算相同的值
  - 第 346 行 `mc_low += s2value;` —— 第二次加相同的舍入贡献

  同一舍入修正值被加了两次，导致 `mc_low` 值偏大，最终乘法结果产生 1 ULP 以上的误差。同时进位检测 `p` 使用的是第一次累加后的 `mc_low`，逻辑上也存在矛盾。
- **触发条件**: 当乘积尾数最高有效位恰好位于 bit 20（即 `n == EXP_OFFSET == 20`，`lshift == 0`）时触发。例如两个尾数乘积的 s3 的最高位恰好在 bit 20。
- **测试方案**: 构造使得 `s3` 的 MSB 恰好在 bit 20 的输入对（如 `1.0 * 1.5` 等规格化数乘积），对比 IEEE 754 标准库 `double` 乘法结果，检查 ULP 误差。

### Bug 4: MulUint8Op 中 AndFF 类型不匹配

- **位置**: 第 461 行
- **类型**: 类型不匹配
- **严重程度**: 中
- **描述**: `Y` 的输出类型为 `uint32_t`（由 `Vec::Mul<uint32_t>` 产生），但 `Y1` 使用 `AndFF<int32_t>` 接收。`AndFF` 的输入输出均声明为同一类型 `T`（此处为 `int32_t`），将 `uint32_t` 数据传入 `int32_t` 处理会导致类型安全问题。在 DAG 绑定时可能引发编译错误或隐式符号扩展错误，大值 `uint32_t` 被当作负数处理。
- **触发条件**: `uint8_t` 输入值较大时（如 200 * 200 = 40000），乘积在 `uint32_t` 中表示正确，但被 `int32_t` 解释时可能影响 And 操作的语义（虽然位操作不受符号影响，但类型系统不匹配会导致编译期问题）。
- **测试方案**: 编译 MulUint8Op 路径，确认是否有模板类型推导错误；运行时测试 `255 * 255` 等边界值。

---

### Bug 5: __builtin_clz(0) 未定义行为

- **位置**: 第 266 行
- **类型**: 未定义行为 (UB)
- **严重程度**: 低
- **描述**: 当 `total_shift == 0` 且乘积为零（第 221-224 行的 else 分支设置 `s3 = 0`）时，第 266 行调用 `__builtin_clz(s3)` 即 `__builtin_clz(0)`，其行为在 C/C++ 标准中是未定义的。虽然理论上在零检查（第 158-167 行）后不应出现乘积为零的情况，但若输入构造不当或未来修改引入路径，可能触发 UB。
- **触发条件**: 理论上在当前逻辑中不可达（非零输入保证乘积非零），但属于潜在防御性编程缺陷。
- **测试方案**: 使用 UBSan（Undefined Behavior Sanitizer）运行全覆盖测试，或在第 266 行前添加 `s3 == 0` 的防护检查。
