# Mul DAG 算子代码审查报告

## Bug 列表

### Bug 1: 规格化数 lshift==0 分支舍入值被重复累加

- **位置**: 第 339-348 行，`MulDouble_vf` 函数，规格化数处理 `else`（lshift==0）分支
- **类型**: DAG逻辑/精度错误
- **严重程度**: 高
- **描述**: 当 `lshift == 0` 时，`mc_low` 先被赋值为 `s2`，然后加上了来自 `s1` 的舍入值 `((s1 >> 1) + (1 << 30)) >> 31`。随后代码又计算了完全相同的 `s2value = ((s1 >> 1) + (1 << 30)) >> 31`，并再次将其加到 `mc_low` 上（第二次累加），同时还做了进位检测。这导致舍入修正被应用了两次，产生错误的尾数结果。
- **触发条件**: 当两个 double 相乘，乘积的 `s3` 最高有效位恰好在 bit 20（即 `n == EXP_OFFSET == 20`，`lshift = 0`）时触发。例如两个接近 1.0 的 normal double 相乘。
- **测试方案**: 对 `1.0 * 1.0`、`1.5 * 1.5`、`1.999... * 1.0` 等乘积使 n=20 的用例进行精度对比测试，与标准 IEEE 754 double 乘法结果比较 ULP 差异。

### Bug 2: NaN 输出时 c.i[0] 未初始化

- **位置**: 第 121-129 行、第 133-135 行、第 146-149 行
- **类型**: 精度/未定义行为
- **严重程度**: 中
- **描述**: 当检测到输入为 NaN 或 inf*0 时，代码仅设置 `c.i[1] = NANI` 后就将 `c.d` 写入输出。但 `c` 是栈上局部变量，`c.i[0]`（double 的低 32 位）从未被初始化，其值不确定。这导致输出的 NaN 的 payload 包含随机垃圾值，虽然仍是 NaN，但违反确定性要求，可能导致位精度测试失败。
- **触发条件**: 任意一个输入为 NaN，或出现 inf * 0 的情况。
- **测试方案**: 输入 NaN 或 inf*0，检查输出是否为标准 quiet NaN（`0x7FF8000000000000`），多次运行检查输出是否一致。

### Bug 3: 零值乘法结果丢失符号位

- **位置**: 第 158-167 行
- **类型**: 精度错误（IEEE 754 合规性）
- **严重程度**: 中
- **描述**: 当检测到输入为零时，直接赋值 `c.d = 0`（正零）输出，没有根据两个输入的符号位 `sa ^ sb` 计算结果的符号。按 IEEE 754 标准：`(-0) * 正数 = -0`，`(-0) * (-0) = +0`，`正数 * (-0) = -0`。当前实现始终返回 `+0`。
- **触发条件**: 任一输入为 `-0.0`，另一输入为非零有限数或 `-0.0`。例如 `-0.0 * 5.0` 应得 `-0.0`，实际得 `+0.0`。
- **测试方案**: 测试 `-0.0 * 1.0`、`-0.0 * -1.0`、`0.0 * -5.0`，用 `memcmp` 或检查符号位验证结果的符号是否正确。

### Bug 4: MulUint8Op 中 AndFF 模板类型不匹配

- **位置**: 第 461 行
- **类型**: DAG逻辑/类型安全
- **严重程度**: 中
- **描述**: `MulUint8Op` 的乘法节点 `Y` 的输出类型为 `uint32_t`（由 `Vec::Mul<uint32_t>` 产生），但下一个节点 `Y1` 使用的是 `AndFF<int32_t>`，其输入输出类型均为 `int32_t`。将 `uint32_t` 隐式传递给期望 `int32_t` 的模板节点存在类型不匹配。注释中被注释掉的 `// using Y1 = Bind<AndFF<uint32_t>, Y>;` 才是正确的写法。对于大于 `INT32_MAX` 的 `uint32_t` 值，有符号解释会导致未定义行为或意外的位操作结果。
- **触发条件**: 两个较大的 `uint8_t` 值相乘（如 `200 * 200 = 40000`），其 `uint32_t` 结果在 DAG 中被作为 `int32_t` 处理时可能触发问题。
- **测试方案**: 测试 `uint8_t` 边界值乘法如 `255 * 255`，验证截断后结果是否正确为 `(255*255) & 0xFF = 1`。

### Bug 5: MulBoolOp 使用了错误的 Cast 舍入模式

- **位置**: 第 480 行
- **类型**: Cast模式错误
- **严重程度**: 低
- **描述**: `MulBoolOp` 中 `half -> int8_t` 的类型转换使用了 `CAST_MODE_ROUND`（值为 4），而其他类似的降精度转换（如 `MulXfp16Op` 中的 `float -> half`）使用的是 `CAST_MODE_RINT`（值为 1）。`CAST_MODE_ROUND` 对应 `RoundMode::CAST_ROUND`（四舍五入），而 `CAST_MODE_RINT` 对应银行家舍入（round to nearest even）。对于布尔运算，虽然理论上 0.0/1.0 的转换不受舍入模式影响，但若中间计算出现浮点误差（如 0.999...），`ROUND` 模式可能将其错误舍入为 1，而标准做法应使用 `CAST_MODE_RINT` 或截断模式保证确定性。
- **触发条件**: 当 bool 以 int8_t 存储且值不严格为 0/1 时（如框架传入 2），中间 half 乘法结果可能产生非整数值，此时不同舍入模式产生不同结果。
- **测试方案**: 构造 bool tensor 中含有非标准值（如 2、-1），验证乘法结果是否符合预期语义。
