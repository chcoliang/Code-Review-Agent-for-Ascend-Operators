# Mul DAG 代码审查报告

## Bug 列表

### Bug 1: NaN 结果低32位未初始化

- **位置**: 第 122-129 行, 第 133-137 行, 第 146-149 行
- **类型**: 未初始化变量
- **严重程度**: 高
- **描述**: 当检测到 NaN 或 inf*0 时，代码只设置了 `c.i[1] = NANI`，但从未初始化 `c.i[0]`。`U c;` 是栈上局部变量，`c.i[0]` 包含随机垃圾值，导致输出的 double 值的低 32 位不确定。IEEE 754 标准 NaN 的低位应为 0。
- **触发条件**: 任一输入为 NaN，或 inf * 0 的情况。
- **测试方案**: 输入 `NaN * 1.0` 或 `inf * 0.0`，检查输出的 double 位模式低 32 位是否为 0（即标准 quiet NaN）。

### Bug 2: 零值乘法丢失符号位

- **位置**: 第 158-167 行
- **类型**: 逻辑错误
- **严重程度**: 中
- **描述**: 当 a 或 b 为零时，代码直接设置 `c.d = 0`，结果始终为 +0。但 IEEE 754 规定乘法结果的符号是两个操作数符号的异或。例如 `(-0.0) * 5.0` 应返回 `-0.0`，`(-3.0) * 0.0` 应返回 `-0.0`，但当前实现均返回 `+0.0`。
- **触发条件**: 任一操作数为零，且两操作数符号不同时（如负数乘以零、负零乘以正数）。
- **测试方案**: 计算 `(-1.0) * 0.0`，验证结果为 `-0.0`（符号位为1）；计算 `(-0.0) * (-0.0)`，验证结果为 `+0.0`。

### Bug 3: `__builtin_clz(0)` 未定义行为

- **位置**: 第 266 行
- **类型**: 未定义行为 (UB)
- **严重程度**: 高
- **描述**: 当乘积结果为零时（s3=s2=s1=s0=0），代码在第 221-224 行的 else 分支设置 `total_shift = 0; s3 = 0;`，随后在第 266 行执行 `__builtin_clz(s3)`。`__builtin_clz(0)` 的行为是未定义的（GCC/Clang文档明确说明参数为0时结果未定义）。这可能导致崩溃或错误的 `n` 值。
- **触发条件**: 两个 subnormal 数相乘结果下溢为零（如极小的 subnormal 相乘）。虽然前面有零值判断，但 subnormal 的 `INT32_MMAXMASK` 检查不能完全覆盖此情况（subnormal 的高位非零但乘积可能为零）。
- **测试方案**: 构造两个极小 subnormal double 值相乘，使 128 位乘积为全零，观察是否触发 UB 或异常。

### Bug 4: 规格化数 lshift==0 分支中舍入值被重复累加

- **位置**: 第 339-348 行
- **类型**: 逻辑错误（重复计算）
- **严重程度**: 高
- **描述**: 在规格化数处理的 `lshift == 0`（即 `n == EXP_OFFSET == 20`）分支中：
  - 第 341 行: `mc_low = s2;`
  - 第 342 行: `mc_low += ((s1 >> 1) + (1 << 30)) >> 31;`（第一次加舍入进位）
  - 第 344 行: `s2value = ((s1 >> 1) + (1 << 30)) >> 31;`（与第 342 行完全相同的值）
  - 第 346 行: `mc_low += s2value;`（第二次加同样的舍入进位）
  
  舍入进位被加了两次，导致结果偏大。同时 `p` 的溢出检测（第 345 行）基于已经被第一次加法修改后的 `mc_low`，判断也不正确。
- **触发条件**: 两个 double 数相乘，乘积的 MSB 恰好在 bit 20 位置（即 `n == 20`），且 s1 足够大使舍入进位为 1 时。
- **测试方案**: 构造使 `n=20` 且 `s1 >= 0x80000000` 的乘法输入（如两个尾数特定的 double），对比硬件/软件参考实现结果。

### Bug 5: MulUint8Op 中 AndFF 类型不匹配

- **位置**: 第 461 行
- **类型**: 类型不匹配
- **严重程度**: 中
- **描述**: `MulUint8Op` 中乘法结果 `Y` 的类型为 `uint32_t`（由 `Vec::Mul<uint32_t>` 产生），但随后使用 `Bind<AndFF<int32_t>, Y>` 进行掩码操作。`AndFF<int32_t>` 期望输入输出为 `LocalTensor<int32_t>`，将 `uint32_t` tensor 传入可能导致编译错误或隐式类型转换问题。注释中已标注正确写法应为 `AndFF<uint32_t>`（第 463 行被注释掉的代码）。
- **触发条件**: 编译 `MulUint8Op` DAG 时，如果框架严格检查类型一致性则编译失败；若隐式转换则在有符号/无符号边界值（如 128-255）可能产生错误结果。
- **测试方案**: 输入 `uint8_t` 值 200 和 2，期望结果 `(200*2) & 0xFF = 144`，检查是否正确。

### Bug 6: SIGNMASK 常量有符号整型溢出

- **位置**: 第 34 行
- **类型**: 实现定义行为 / 潜在溢出
- **严重程度**: 低
- **描述**: `constexpr int SIGNMASK = 0x80000000;` — 在 32 位 int 平台上，`0x80000000` (2147483648) 超出 `int` 最大值 (2147483647)。C++ 标准规定这是实现定义行为。虽然大多数平台以二进制补码方式存储为 INT_MIN，代码逻辑依赖此行为可以工作，但不符合严格标准合规性，部分编译器会发出警告。
- **触发条件**: 在严格合规编译器或非二进制补码平台上编译时可能报错或产生意外值。
- **测试方案**: 使用 `-Wpedantic -Werror` 编译选项检查是否有警告；建议改为 `constexpr unsigned int SIGNMASK = 0x80000000u;`。
