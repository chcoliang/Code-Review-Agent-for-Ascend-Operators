# Mul DAG 算子代码审查报告

## Bug 列表

### Bug 1: NaN/Inf 结果低32位未初始化

- **位置**: 第121-155行，`MulDouble_vf` 函数中 NaN 和 Inf 处理分支
- **类型**: 未初始化变量
- **严重程度**: 高
- **描述**: 当检测到输入为 NaN 或 `inf * 0` 时，代码仅设置 `c.i[1] = NANI`，但从未初始化 `c.i[0]`。`U c;` 是栈上局部变量，`c.i[0]` 包含未定义的垃圾值，导致输出的 NaN 的低32位不确定。IEEE 754 标准的 canonical NaN 应该是确定值。
- **触发条件**: 任一输入为 NaN，或两个输入分别为 Inf 和 0 时触发。
- **测试方案**: 输入 `(NaN, 1.0)`, `(Inf, 0.0)`, `(0.0, Inf)`，验证输出的完整64位是否为标准 NaN（`0x7FF8000000000000`）。

### Bug 2: 零乘法结果丢失符号位

- **位置**: 第158-167行，零值处理分支
- **类型**: 逻辑错误
- **严重程度**: 中
- **描述**: 当输入 `a` 或 `b` 为零时，结果直接设为 `c.d = 0`（即 +0.0）。根据 IEEE 754 规范，零乘法的结果符号应为 `sign(a) XOR sign(b)`。例如 `(-0.0) * 5.0` 应返回 `-0.0`，但当前代码返回 `+0.0`。
- **触发条件**: 任一输入为 `+0.0` 或 `-0.0` 且另一输入为有限非零数（或同为零）。
- **测试方案**: 输入 `(-0.0, 1.0)` 验证输出为 `-0.0`；输入 `(-0.0, -1.0)` 验证输出为 `+0.0`；通过检查符号位确认正确性。

### Bug 3: 规格化数 lshift==0 分支双重舍入（重复加法）

- **位置**: 第339-348行，规格化数处理中 `lshift == 0` 的 else 分支
- **类型**: 逻辑错误（重复计算）
- **严重程度**: 高
- **描述**: 该分支对 `mc_low` 执行了两次相同的舍入加法：
  - 第342行: `mc_low += ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32;`
  - 第344-346行: 又计算相同的 `s2value` 并再次执行 `mc_low += s2value;`

  对比 `lshift > 0` 和 `lshift < 0` 分支的正确模式（先赋值 `mc_low`，再一次性加入舍入值并处理进位），此处第342行是多余的，导致舍入值被加了两次，产生精度错误。正确代码应删除第342行的加法。
- **触发条件**: 乘法结果的 MSB 恰好在第20位（即 `n == EXP_OFFSET == 20`），使 `lshift = 0`。当两个接近 1.0 的 normal double 相乘时容易触发。
- **测试方案**: 输入 `(1.0, 1.0)`、`(1.5, 1.0)` 等使 s3 的最高有效位恰好在 bit 20 的用例，对比标准 IEEE 754 双精度乘法结果，验证低位是否正确。

### Bug 4: MulUint8Op 中类型不匹配

- **位置**: 第461行，`MulUint8Op` 结构体
- **类型**: 类型不匹配
- **严重程度**: 中
- **描述**: `Y` 的类型为 `Vec::Mul<uint32_t>` 输出 `uint32_t`，但接下来 `Y1 = Bind<AndFF<int32_t>, Y>` 使用 `AndFF<int32_t>` 操作，其模板参数为 `int32_t`。将 `uint32_t` 数据传入期望 `int32_t` 的操作可能导致：(1) 编译期类型推导错误；(2) 当高位为1时，有符号解释产生负数，后续行为不确定。注释中 `// using Y1 = Bind<AndFF<uint32_t>, Y>;` 表明开发者意识到了问题但未修正。
- **触发条件**: `uint8_t` 输入相乘结果 > 127（如 `200 * 2 = 400`），高位为1时有符号/无符号解释不同。
- **测试方案**: 输入 `(200, 2)`, `(255, 255)` 等大值 uint8 对，验证截断后低8位结果是否正确（应为模256结果）。

### Bug 5: `__builtin_clz(s3)` 在 s3==0 时未定义行为

- **位置**: 第266行
- **类型**: 未定义行为（UB）
- **严重程度**: 低
- **描述**: 当 `total_shift` 逻辑的 else 分支（第221-224行）被执行时，`s3` 被设为0，随后第266行调用 `__builtin_clz(s3)` 产生未定义行为（C/C++ 标准规定 `__builtin_clz(0)` 结果未定义）。虽然理论上在排除零输入后不会出现全零乘积，该 else 分支作为防御性代码路径仍存在 UB 风险。
- **触发条件**: 理论上不可达（因为已排除零输入），但若代码逻辑被重构或前置检查被修改，该 UB 可能暴露。
- **测试方案**: 静态分析工具检测；或人为注入 s3=0 的场景验证运行时行为。
