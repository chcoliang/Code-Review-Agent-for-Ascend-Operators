# Mul DAG 算子代码审查报告

## Bug 列表

### Bug 1: NANI 常量值错误，无法正确生成 NaN

- **位置**: 第 37 行 `constexpr int NANI = 0x00000000;`，影响第 122-129、134-138、146-150 行
- **类型**: 逻辑错误
- **严重程度**: 严重 (Critical)
- **描述**: `NANI` 被定义为 `0x00000000`，当代码需要返回 NaN 时执行 `c.i[1] = NANI`，结果高32位为0，这根本不是IEEE 754的NaN表示。IEEE 754 double的 quiet NaN 高32位应为 `0x7FF80000`（指数全1且尾数非零）。当前实现会将 NaN 结果错误地输出为接近零的值或未定义值。
- **触发条件**: 任何输入为 NaN 的情况（如 `NaN * 1.0`），或 `inf * 0` 的情况。
- **测试方案**: 输入 `src1 = [NaN]`, `src2 = [1.0]`，验证输出是否为 NaN；输入 `src1 = [inf]`, `src2 = [0.0]`，验证输出是否为 NaN。

### Bug 2: 返回 NaN 时 c.i[0] 未初始化

- **位置**: 第 122-125、127-129、134-137、146-149 行
- **类型**: 未初始化变量
- **严重程度**: 严重 (Critical)
- **描述**: 当检测到 NaN 或 `inf*0` 时，代码仅设置 `c.i[1] = NANI`，但未设置 `c.i[0]`。由于 `U c;` 是局部变量且未初始化，`c.i[0]` 包含栈上的随机值。即使 `NANI` 被修正为正确值，低32位仍然是垃圾数据，导致输出不确定。
- **触发条件**: 同 Bug 1，任何触发 NaN 返回路径的输入。
- **测试方案**: 多次执行 `NaN * 1.0`，观察结果的低32位是否一致（不一致说明使用了未初始化内存）。

### Bug 3: 零值乘法结果丢失符号位

- **位置**: 第 158-167 行
- **类型**: 逻辑错误（IEEE 754 合规性）
- **严重程度**: 中等 (Medium)
- **描述**: 当检测到操作数之一为零时，直接赋值 `c.d = 0`，结果始终为 +0.0。根据 IEEE 754 标准，乘法结果的符号应为两个操作数符号的异或。例如 `-0.0 * 5.0 = -0.0`，`-3.0 * 0.0 = -0.0`，但当前实现会错误返回 `+0.0`。
- **触发条件**: 一个操作数为零且另一个操作数为负数，例如 `src1 = [-1.0]`, `src2 = [0.0]`。
- **测试方案**: 计算 `-1.0 * 0.0`，用 `signbit()` 检查结果是否为负零；计算 `-0.0 * -0.0`，验证结果为 `+0.0`。

### Bug 4: `__builtin_clz(0)` 未定义行为

- **位置**: 第 266 行 `int n = NOSIGN_OFFSET_32 - __builtin_clz(s3);`
- **类型**: 未定义行为 (UB)
- **严重程度**: 严重 (Critical)
- **描述**: 当乘积结果为零（所有 s3/s2/s1/s0 都为0）时，`total_shift` 在第 222-224 行的 else 分支中被设为 0，`s3` 被设为 0。随后第 266 行调用 `__builtin_clz(s3)` 即 `__builtin_clz(0)`，根据 C/C++ 标准这是未定义行为，可能返回任意值或导致崩溃。
- **触发条件**: 两个非零的 subnormal 数相乘，且乘积下溢为零（极小 subnormal 互乘）。虽然正常零已在第 158-167 行提前返回，但两个极小 subnormal 通过零检查后乘积可能为全零。
- **测试方案**: 输入两个最小 subnormal double 值（如 `5e-324 * 5e-324`），检查是否触发异常或返回非确定性结果。

### Bug 5: 规格化数 lshift==0 分支中舍入值被重复累加

- **位置**: 第 339-348 行（`else` 分支，即 `lshift == 0` 时）
- **类型**: 逻辑错误
- **严重程度**: 严重 (Critical)
- **描述**: 在规格化数处理的 `lshift == 0` 分支中：
  - 第 341 行：`mc_low = s2;`
  - 第 342 行：`mc_low += ((s1 >> 1) + (1 << 30)) >> 31;` — 第一次加入舍入进位
  - 第 344 行：`unsigned int s2value = ((s1 >> 1) + (1 << 30)) >> 31;` — 计算相同的值
  - 第 346 行：`mc_low += s2value;` — 第二次加入相同的舍入进位

  舍入进位被添加了两次，导致 `mc_low` 偏大，最终乘法结果偏大（最多偏差 1 ULP 以上）。对比其他分支（lshift > 0 和 lshift < 0），它们只添加一次舍入值。
- **触发条件**: 任何触发 `lshift == 0`（即 `n == 20`，即 s3 最高位恰好在 bit 20）的规格化乘法，例如尾数乘积的最高有效位恰好在第 52 位。
- **测试方案**: 找到使 `n == EXP_OFFSET(20)` 的输入对（如 `1.0 * 1.5`，其中 ma=0x100000, mb=0x180000），对比硬件 double 乘法结果，验证最低有效位是否多了 1。

### Bug 6: MulUint8Op 中 AndFF 类型不匹配

- **位置**: 第 461 行 `using Y1 = Bind<AndFF<int32_t>, Y>;`
- **类型**: 类型不匹配
- **严重程度**: 中等 (Medium)
- **描述**: `Y` 的类型是 `Vec::Mul<uint32_t>` 的输出（即 `uint32_t`），但 `AndFF<int32_t>` 期望输入类型为 `int32_t`（`LocalTensor<int32_t>`）。在 DAG 框架中，这可能导致编译错误或隐式类型重解释。注释中已有 `// using Y1 = Bind<AndFF<uint32_t>, Y>;` 提示正确写法应使用 `uint32_t`。
- **触发条件**: 编译并使用 `MulUint8Op` 路径处理 uint8 乘法时。
- **测试方案**: 编译 uint8 乘法路径，验证是否有类型不匹配的编译告警；运行 `200 * 2` (uint8) 验证截断结果是否正确为 144。
