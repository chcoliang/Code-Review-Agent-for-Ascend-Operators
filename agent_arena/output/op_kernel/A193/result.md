# Ascend NPU 算子代码审查报告 - mul_dag.h (A193)

## Bug 列表

### Bug 1: NaN 结果低 32 位未初始化

- **位置**: 第 121-129 行、第 133-137 行、第 145-149 行
- **类型**: 未初始化变量 / 数据正确性
- **严重程度**: 高
- **描述**: 当检测到 NaN 或 `inf * 0` 时，代码只设置了 `c.i[1] = NANI`，但从未初始化 `c.i[0]`。联合体 `U c;` 声明后 `c.i[0]` 包含栈上的垃圾值，导致输出的 double NaN 的低 32 位不确定。IEEE 754 规范中 NaN 的 payload 应是确定的，且不同线程可能产生不一致的 NaN 表示。
- **触发条件**: 输入包含 NaN 值，或一个操作数为 inf 另一个为 0。
- **测试方案**: 构造输入 `src1 = NaN, src2 = 1.0`，检查输出是否为标准 quiet NaN（`0x7FF8000000000000`）。同理测试 `inf * 0` 场景。

### Bug 2: 零值乘法结果丢失符号位

- **位置**: 第 158-167 行
- **类型**: 逻辑错误 / IEEE 754 合规性
- **严重程度**: 高
- **描述**: 当任一操作数为零时，代码直接返回 `c.d = 0`（正零）。但 IEEE 754 要求乘法结果的符号位为两操作数符号的异或。例如 `(-0.0) * 5.0` 应返回 `-0.0`，`(-3.0) * 0.0` 应返回 `-0.0`，但当前实现始终返回 `+0.0`。
- **触发条件**: 任一操作数为 +0 或 -0，另一操作数为负数或 -0。
- **测试方案**: 测试 `(-1.0) * 0.0` 期望结果为 `-0.0`（`0x8000000000000000`）；测试 `(-0.0) * (-0.0)` 期望结果为 `+0.0`。

---

### Bug 3: 规格化数 lshift==0 分支对 mc_low 重复累加舍入值

- **位置**: 第 339-348 行
- **类型**: 逻辑错误 / 计算精度
- **严重程度**: 高
- **描述**: 在规格化数处理的 `lshift == 0` (即 `n == EXP_OFFSET == 20`) 分支中：
  ```cpp
  mc_high = s3 - (1 << EXP_OFFSET);
  mc_low = s2;
  mc_low += ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32; // 第一次加
  
  unsigned int s2value = ((s1 >> 1) + (1 << HIGH_BIT_OFFSET_32)) >> NOSIGN_OFFSET_32;
  int p = (~mc_low < s2value);
  mc_low += s2value; // 第二次加同样的值！
  mc_high += p;
  ```
  舍入修正值 `s2value` 被加了两次到 `mc_low`。对比 `lshift > 0` 和 `lshift < 0` 分支的逻辑模式，`mc_low` 应该只在第二次（带进位检测的）处加值，第一次 `mc_low = s2` 后不应有额外累加。这会导致尾数偏大，产生精度错误或进位错误。
- **触发条件**: 两个 double 相乘使得乘积尾数的最高有效位恰好在 bit 20 位置（`n == 20`，即 `s3` 的最高位为 bit 20）。
- **测试方案**: 构造两个 double 使乘积的 `s3` 最高位恰好在 bit 20，例如尾数接近 `1.0 * 1.0`（都是规格化数且隐含位为1），与标准库 `double` 乘法结果对比最后几位 ULP。

### Bug 4: MulUint8Op 中类型不匹配 - AndFF<int32_t> 作用于 uint32_t 数据

- **位置**: 第 461 行
- **类型**: 类型不匹配
- **严重程度**: 中
- **描述**: `MulUint8Op` 中乘法使用 `Vec::Mul<uint32_t>` 产出 `uint32_t` 类型的 tensor，但下一步使用 `AndFF<int32_t>` 处理。`Bind<AndFF<int32_t>, Y>` 中 `Y` 的输出类型是 `uint32_t`，而 `AndFF<int32_t>` 期望输入类型为 `int32_t`（`LocalTensor<int32_t>`）。这导致 DAG 类型推导时输入输出类型不一致，可能引发编译错误或在某些平台上产生隐式符号扩展/截断问题。注释中已标注了正确做法 `// using Y1 = Bind<AndFF<uint32_t>, Y>;` 但未启用。
- **触发条件**: 编译使用 `MulUint8Op` 的代码路径，输入为 `uint8_t` 类型数据。
- **测试方案**: 使用 uint8_t 输入（例如 200 * 2 = 400，截断后应为 144），验证是否能正确编译并产出正确结果；与 `AndFF<uint32_t>` 版本对比。

---

### Bug 5: MulBoolOp 使用错误的 CAST_MODE_ROUND 舍入模式

- **位置**: 第 480 行
- **类型**: 逻辑错误 / 语义不当
- **严重程度**: 低
- **描述**: `MulBoolOp` 将 half 类型结果转回 int8_t 时使用了 `CAST_MODE_ROUND`（值为 4）。根据代码顶部常量定义，有效的模式为 `CAST_MODE_NONE(0)`、`CAST_MODE_RINT(1)`、`CAST_MODE_FLOOR(2)`、`CAST_MODE_ROUND(4)`。对于布尔乘法（逻辑AND），结果只有 0 和 1，理论上各模式等价，但 `CAST_MODE_ROUND=4` 对应的 RoundMode 枚举值可能不是预期的 `CAST_ROUND`，存在平台兼容性风险。更合适的应该是 `CAST_MODE_RINT` 以与其他类似模板保持一致。
- **触发条件**: 输入为 bool 类型（int8_t 表示）。在某些硬件版本中如果 CAST_MODE_ROUND 映射到非法 RoundMode 会出错。
- **测试方案**: bool 类型输入 `[true, false] * [true, true]`，验证输出为 `[1, 0]`，在多种硬件版本上回归。
