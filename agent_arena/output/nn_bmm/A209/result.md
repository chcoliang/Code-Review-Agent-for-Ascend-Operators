# BMM Stress Test 代码审查报告

## Bug 1: 循环内存分配未释放导致严重内存泄漏

- **位置**: 第 9 行 (`aclrtMalloc(&ws, 32*1024*1024, ACL_MEM_MALLOC_HUGE_FIRST);`)
- **类型**: 内存泄漏
- **严重程度**: 高
- **描述**: 在 `for` 循环（500次迭代）中，每次迭代分配 32MB 设备内存，但循环体内没有对应的 `aclrtFree(ws)` 调用。由于 `ws` 是循环局部变量，每次迭代覆盖前一次的指针值，导致之前分配的内存永远无法释放。总计泄漏 500 * 32MB = 16GB 设备内存。
- **触发条件**: 程序正常执行即触发。在 Ascend 910B 上设备内存有限（通常 32GB HBM），16GB 的泄漏极可能导致 OOM。
- **测试方案**: 运行程序并监控 NPU 设备内存使用（通过 `npu-smi info`），观察内存持续增长且程序退出后设备内存未归还（直到 `aclrtResetDevice`）。也可在循环次数较少时检查 `aclrtMalloc` 返回值是否为 `ACL_ERROR_RT_MEMORY_ALLOCATION`。

## Bug 2: 未检查 aclInit 返回值

- **位置**: 第 3 行 (`aclInit(nullptr);`)
- **类型**: 错误处理缺失
- **严重程度**: 中
- **描述**: `aclInit` 可能失败（如环境未正确配置），未检查返回值。后续所有 ACL 调用在初始化失败时行为未定义。
- **触发条件**: ACL 运行时环境异常、驱动未加载等情况下 `aclInit` 失败。
- **测试方案**: 在未安装驱动的环境中运行，验证程序是否安全退出而非崩溃。

## Bug 3: 未检查 aclrtSetDevice 返回值

- **位置**: 第 4 行 (`aclrtSetDevice(0);`)
- **类型**: 错误处理缺失
- **严重程度**: 中
- **描述**: 设备设置失败（如设备不存在或被占用）时未处理，后续操作会在无效设备上下文中执行。
- **触发条件**: 设备 0 不可用、已被独占等。
- **测试方案**: 在无 NPU 设备的环境中运行，观察程序行为。

## Bug 4: 未检查 aclrtCreateStream 返回值

- **位置**: 第 6 行 (`aclrtCreateStream(&stream);`)
- **类型**: 错误处理缺失
- **严重程度**: 中
- **描述**: Stream 创建失败时 `stream` 变量未初始化（为栈上随机值），后续 `aclrtDestroyStream(stream)` 会传入无效指针，可能导致未定义行为或崩溃。
- **触发条件**: 设备资源耗尽、前序设备初始化失败。
- **测试方案**: Mock `aclrtCreateStream` 返回失败，验证程序是否崩溃。

## Bug 5: 未检查 aclrtMalloc 返回值

- **位置**: 第 9 行 (`aclrtMalloc(&ws, 32*1024*1024, ACL_MEM_MALLOC_HUGE_FIRST);`)
- **类型**: 错误处理缺失
- **严重程度**: 中
- **描述**: 500次大块内存分配中，任何一次都可能因内存不足而失败，但返回值未被检查。分配失败后 `ws` 仍为 `nullptr`，若后续有使用（当前代码虽无使用，但设计意图显然是要使用的）会导致空指针访问。
- **触发条件**: 设备内存不足时（由于前面的泄漏，在约第 ~1000次迭代后必然触发，具体取决于设备内存大小）。
- **测试方案**: 增大循环次数或减小设备可用内存，检查 `aclrtMalloc` 返回错误码。

## Bug 6: 循环结束后 ws 指针作用域丢失

- **位置**: 第 8-11 行（循环体）
- **类型**: 资源管理设计缺陷
- **严重程度**: 低
- **描述**: `ws` 声明在循环体内，循环结束后最后一次分配的内存指针也丢失，即使想在循环后释放也无法做到。正确做法应在循环内 `aclrtFree(ws)` 或用容器收集所有指针。
- **触发条件**: 代码结构性问题，始终存在。
- **测试方案**: 代码静态分析即可发现。
