# Code Review: aclnn_scaled_masked_softmax.cpp (A143)

## Bug 列表

### Bug 1: 错误信息硬编码，与实际限制值不一致

- **位置**: 第 105 行
- **类型**: 逻辑错误 / 信息误导
- **严重程度**: 中
- **描述**: 错误日志消息硬编码为 `"Expected x and mask dim4 in range of (0, 4096]."`, 但在 ASCEND910_95 平台上，实际限制值 `dDimLimit` 为 8192 (`D_LIMIT_D`)。当用户在 910_95 平台上传入 dim3 为 5000 的张量时，报错提示 4096 是错误的，应提示 8192。
- **触发条件**: 在 ASCEND910_95 平台上，输入 x 的第 4 维大于 4096 但小于等于 8192 时不会报错（正确行为），但若大于 8192 时报错信息仍显示 4096，造成误导。
- **测试方案**: 在 ASCEND910_95 平台上构造 dim3 = 9000 的输入张量，验证报错信息是否正确显示上限为 8192。

### Bug 2: extern 函数声明放在匿名命名空间内导致链接问题

- **位置**: 第 39-44 行
- **类型**: 编译/链接错误
- **严重程度**: 高
- **描述**: `aclnnInnerScaledMaskedSoftmaxV2GetWorkspaceSize` 和 `aclnnInnerScaledMaskedSoftmaxV2` 两个外部函数的 `extern` 声明被放置在匿名命名空间 (`namespace { }`) 内。匿名命名空间赋予其中声明的实体内部链接 (internal linkage)，这与 `extern` 关键字所表示的外部链接 (external linkage) 相矛盾。根据 C++ 标准，这会导致未定义行为或链接失败，编译器可能无法找到这些函数的外部定义。
- **触发条件**: 编译时链接器可能报 undefined reference 错误，或者在某些编译器实现下静默通过但运行时行为未定义。
- **测试方案**: 使用严格模式编译 (`-pedantic -Werror`)，检查是否产生链接错误。将这两个 extern 声明移到匿名命名空间外部。

### Bug 3: 输出张量 y 的 shape 未与输入 x 进行一致性校验

- **位置**: 第 74-110 行 (`CheckShape` 函数) 及第 112-122 行 (`CheckParams` 函数)
- **类型**: 校验缺失
- **严重程度**: 中
- **描述**: `CheckShape` 仅校验了 `x` 和 `mask` 之间的形状关系，但从未校验输出张量 `y` 的形状是否与 `x` 一致。如果用户传入了形状不匹配的 `y` 张量，可能导致越界写入或计算结果错误。
- **触发条件**: 用户传入 `y` 的 shape 与 `x` 不同（例如维度更小），内核写入时发生越界内存访问。
- **测试方案**: 构造 x shape 为 [2,4,8,64]、y shape 为 [1,1,1,1] 的输入，调用该算子，检查是否触发内存越界或 coredump。

### Bug 4: `extern "C"` 包裹了包含 C++ 特性的匿名命名空间

- **位置**: 第 25-27 行和第 145-147 行
- **类型**: 设计缺陷 / 潜在兼容性问题
- **严重程度**: 低
- **描述**: `extern "C"` 块包含了匿名命名空间及其中使用的 `std::initializer_list`、`op::DataType` 等 C++ 特性。虽然 `extern "C"` 主要影响函数的链接名称 (不进行 name mangling)，但将内部实现细节包含在 `extern "C"` 中属于不规范用法。正确做法是仅将需要 C 链接的公开 API 函数放在 `extern "C"` 内，内部辅助代码放在外部。
- **触发条件**: 某些严格的编译器可能对 `extern "C"` 内使用模板或 C++ 类型产生警告。
- **测试方案**: 使用 `-Wall -Wextra -pedantic` 编译，检查是否有相关警告。

### Bug 5: fixedTriuMask 参数处理逻辑 — 仅在为 true 时报错但未说明参数已被废弃

- **位置**: 第 131-134 行
- **类型**: 设计缺陷 / 接口误导
- **严重程度**: 低
- **描述**: `fixedTriuMask` 参数在接口中暴露给用户，但实际仅支持 `false`。当传入 `true` 时返回错误，错误信息有拼写错误 ("suppport" 应为 "support")。更重要的是，即使传入 `false`，第 135 行也硬编码传递 `false` 给内部函数，说明此参数完全无效，但 API 签名仍保留该参数，容易误导用户。
- **触发条件**: 用户传入 `fixedTriuMask = true`。
- **测试方案**: 传入 `fixedTriuMask = true`，验证返回错误码正确且信息无拼写错误。
