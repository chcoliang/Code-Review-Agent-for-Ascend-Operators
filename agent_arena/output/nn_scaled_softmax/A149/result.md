# Code Review: aclnn_scaled_masked_softmax.cpp (A149)

## Bug 列表

### Bug 1: scale 参数未被传递给内部函数

- **位置**: 第136行
- **类型**: 逻辑错误 (参数传递错误)
- **严重程度**: 严重 (Critical)
- **描述**: 函数 `aclnnScaledMaskedSoftmaxGetWorkspaceSize` 接收用户传入的 `scale` 参数，但在调用内部函数 `aclnnInnerScaledMaskedSoftmaxV2GetWorkspaceSize` 时，第三个参数硬编码为 `1.0` 而非传入的 `scale` 变量。这导致无论用户设置什么缩放因子，实际计算始终使用 scale=1.0，softmax 的缩放功能完全失效。
- **触发条件**: 用户传入任何非 1.0 的 scale 值时，计算结果均不正确。例如 `scale=0.125`（常见于 Transformer 中 1/sqrt(d_k)）时，输出与未缩放的 softmax 相同。
- **测试方案**: 设置 scale=0.5，输入已知数据，验证输出是否等于 softmax(0.5 * x) 而非 softmax(1.0 * x)。对比 PyTorch 参考实现结果。

### Bug 2: fixedTriuMask 参数未被传递给内部函数

- **位置**: 第136行
- **类型**: 逻辑错误 (参数传递错误)
- **严重程度**: 中等 (Medium)
- **描述**: 调用内部函数时 `fixedTriuMask` 被硬编码为 `false`。虽然第132-135行当前限制 `fixedTriuMask` 只能为 `false`（否则报错返回），但这种硬编码方式使得未来如果移除该限制，`fixedTriuMask=true` 的功能仍无法正常工作。且当前的错误提示拼写有误（"suppport"），暗示这是一个临时限制。正确做法应传入变量 `fixedTriuMask`。
- **触发条件**: 当前不会触发功能异常（因为有前置检查），但如果未来去掉第132-135行的限制而忘记修改第136行，将导致该参数失效。
- **测试方案**: 移除 fixedTriuMask 的前置限制后，传入 fixedTriuMask=true，验证是否使用上三角掩码。

### Bug 3: 错误日志中 D_LIMIT 描述与实际限制不一致

- **位置**: 第106行
- **类型**: 日志/提示信息错误
- **严重程度**: 低 (Low)
- **描述**: 错误消息固定输出 `"Expected x and mask dim4 in range of (0, 4096]"`，但当平台为 ASCEND910_95 时，实际限制为 8192（`D_LIMIT_D`）。错误消息未反映真实的动态限制值，会误导用户。
- **触发条件**: 在 ASCEND910_95 平台上，当 dim4 值在 (4096, 8192] 范围内时，实际上应该合法，但如果因其他原因触发该错误路径（如 dim4 > 8192），打印的错误信息仍显示上限为 4096。
- **测试方案**: 在 ASCEND910_95 平台上传入 dim4=5000 的合法输入，确认不报错；传入 dim4=9000，确认错误消息中显示正确的上限 8192。

### Bug 4: CheckShape 未校验 x 与 y 的 shape 一致性

- **位置**: 第75-111行 及第113-123行 (`CheckParams` 函数)
- **类型**: 校验遗漏
- **严重程度**: 中等 (Medium)
- **描述**: `CheckParams` 仅校验了 x 与 mask 的 shape 关系，但未校验输出 tensor y 的 shape 是否与 x 一致。如果用户传入 shape 不匹配的 y tensor，可能导致内存越界写入或计算结果截断。
- **触发条件**: 用户传入 y 的 shape 与 x 不同，例如 x shape 为 [2,8,512,64] 而 y shape 为 [2,8,256,64]，可能导致内存越界或数据丢失。
- **测试方案**: 传入 x shape=[2,8,512,64]，y shape=[2,8,256,64]，检查是否报错或出现内存异常。
